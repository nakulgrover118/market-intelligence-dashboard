# Roadmap

Each phase is built, tested, and confirmed before moving to the next.

- [x] **Phase 0 — Scoping & scaffold**: target definition, repo skeleton, FastAPI health check.
- [x] **Phase 1 — Data acquisition & storage**: historical OHLCV for the pilot universe, clean ingestion pipeline, local storage (Parquet), no lookahead in the pipeline itself.
- [x] **Phase 2a/2b — Cleaning & core feature engineering**: raw->processed cleaning (leading bad-price/zero-volume truncation), manual trailing-only technical indicators with no-lookahead tests.
- [x] **Phase 2c — Cross-asset features**: rolling beta/correlation vs Nifty 50, excess return vs Nifty, gold/silver returns, gold/silver ratio.
- [x] **Phase 3 — Labeling**: volatility-scaled fixed-horizon threshold labels; triple-barrier labeling remains a possible future upgrade.
- [x] **Phase 4a/4b — Pooled dataset & purged walk-forward CV**: cross-sectional panel across all 23 instruments; expanding-window annual folds with purge (via `label_end_date`) and embargo.
- [x] **Phase 4c — Baseline model**: logistic regression fit via the Phase 4a/4b infrastructure, evaluated with Brier score / log-loss / ROC-AUC per fold. Initial result at k=0.5: near-random (see findings below).
- [x] **Phase 4d — Diagnostic detour**: investigated the near-random Phase 4c result before building Phase 5 on top of it. Found real signal at a larger label threshold (k=1.5, ROC-AUC ~0.61-0.62) and adopted it as the project's primary target — see findings below.
- [x] **Phase 5 — ML models**: tuned LightGBM via walk-forward CV against the k=1.5 target. Result: real, consistent improvement over both the logistic regression baseline and the untuned gut-check GBM — see findings below.
- [x] **Phase 6 — Calibration**: fit Platt scaling and isotonic regression on top of the tuned LightGBM's raw scores. Result: neither meaningfully improves on the already-reasonably-calibrated raw probabilities — a genuine negative result, documented rather than forced — see findings below.
- [x] **Phase 7 — Explainability**: SHAP (TreeExplainer) on a final full-history LightGBM model. Result: `realized_vol_20d` dominates by ~4x, revealing that a meaningful part of the model's edge is likely volatility mean-reversion interacting with the label's own vol-scaled threshold, not pure directional signal — an important interpretive finding, not just a chart. See below.
- [ ] **Phase 8 — Backtesting & evaluation**: Brier score, log-loss, reliability diagrams; no accuracy-only claims.
- [ ] **Phase 9 — AI narrative layer** (optional): LLM-generated synthesis over quant outputs.
- [ ] **Phase 10 — Dashboard UI**: React frontend consuming the FastAPI backend.
- [ ] **Phase 11 — Tests, CI, deployment docs**.

## Pilot universe (v1) — Indian market

Finalized in Phase 1 (`backend/app/data/universe.py` is the source of truth):

- 23 NSE-listed instruments, fetched via `yfinance`.
- 22 large-cap stocks across IT, Banking, Energy, FMCG, Auto, Pharma, Infrastructure, Metals, Telecom.
- Indices: `^NSEI` (Nifty 50), `^NSEBANK` (Nifty Bank).
- Commodities (ETF proxies — MCX futures are not available via yfinance): `GOLDBEES.NS`, `SILVERBEES.NS`.
- Switched from US to Indian market: same data-source coverage and rigor, more differentiated on a CV, and NSE-native ETF proxies for gold/silver work just as well as the US GLD/SLV pattern would have.

## Key methodology decisions log

- **Target**: `P(forward N-day return >= +theta%)`, N in {5, 20}, calibrated probability output. Fixed-horizon threshold labels now; triple-barrier (López de Prado) as a later upgrade.
- **Label threshold is volatility-scaled, not a fixed %**: `theta(t, N) = k * daily_vol(t) * sqrt(N)`, using the trailing (no-lookahead) `realized_vol_20d`-style daily volatility estimate and standard sqrt-time scaling to the N-day horizon. A fixed % threshold (e.g. "+2% in 5 days") would make class balance swing wildly across 23 instruments with very different volatility (a quiet stock like ITC vs. a volatile one like Tata Steel); vol-scaling keeps "positive" meaning roughly the same statistical thing everywhere.
- **`k` was revised from 0.5 to 1.5 in Phase 4d, based on evidence, not a hunch.** `k=0.5` was originally chosen for being well-balanced (~33% positive rate, tight 30.8%-40.1% band across all 23 instruments) — but Phase 4c's baseline showed that target carried essentially no signal (ROC-AUC ~0.53-0.55). Rather than assume a bigger model would fix that, Phase 4d tested the actual hypothesis: are small moves just noise while larger ones are more predictable? Re-running the *same* walk-forward protocol at k=1.0 and k=1.5 showed ROC-AUC climbing to 0.58 and then 0.61-0.62 respectively, consistently across both horizons and confirmed across all 13 folds once adopted — small, ~0.5-sigma moves on liquid large-caps really are close to a random walk, but larger, less noise-dominated moves have identifiable precursors. `k=1.5` (now `DEFAULT_K`) trades a lower, more imbalanced positive rate (~9%) for a target that's actually learnable. See "Phase 4d" findings below for the full investigation.
- **Labels store their own end-date** (`label_end_date_{n}d`): the actual calendar date each label's forward-return window ends on, not just the label value. Not used yet, but Phase 5's walk-forward CV needs it to *purge* training samples whose label window overlaps a test period — a well-known leakage source in financial ML, since adjacent daily-sampled N-day-forward labels have overlapping windows and are not independent. Cheap to store now; expensive to reconstruct later.
- **Forward-looking labels are still leakage-checked, just differently than features**: a label is *supposed* to look forward (that's what makes it a label), so the "no lookahead" invariance test used for features doesn't apply to `forward_log_return` itself. What's checked instead: the label *threshold* (`volatility_threshold`, built on a trailing vol estimate) passes the same no-lookahead invariance test as any feature, and the last N rows of every instrument are correctly NaN (right-censored, not filled) since there's no real future data for them yet.
- **Validation**: walk-forward / expanding-window CV only. No shuffled k-fold on time series. Must use the NSE trading calendar derived from the data itself, not a generic/US calendar.
- **Stack**: FastAPI + React (chosen over Streamlit/Dash for stronger engineering signal). Python dependency management via plain venv + pyproject.toml (no uv/poetry — kept simple, no extra installs required).
- **Ingestion**: raw layer is immutable (`backend/data/raw/*.parquet`, one file per ticker, gitignored). Validation flags issues (duplicate dates, non-monotonic index, non-positive prices, missing columns) without silently fixing them — cleaning happens in a later, explicit stage.
- **Cleaning**: only truncates *leading* unusable rows (bad core price or zero volume); a bad row appearing mid-series is flagged as a warning, never silently dropped, since dropping from the middle of a time series creates a gap that a `.shift()`-based feature would silently paper over. "Core price" columns are chosen based on what features actually consume (`open` is excluded) — a column-level decision informed by looking at what broke in real data, not a generic "clean everything" rule.
- **Feature engineering**: technical indicators implemented manually in pandas (not a library like pandas-ta or TA-Lib), specifically so every function's trailing-only windowing can be verified rather than trusted. Every indicator has a "no lookahead" test asserting its value at day t is unchanged when more history is appended after t — this is the actual leakage-safety guarantee, not just a spot-checked formula.
- **Cross-asset alignment**: any two instruments are joined via an *inner join* on date before computing a rolling stat (beta, correlation, excess return) — never forward-filled — since a fabricated "flat" day for a missing date would quietly bias the estimate. The result is reindexed back onto each instrument's own calendar, correctly reintroducing NaN wherever the reference series has no data that day.
- **Cross-asset features are computed uniformly for every instrument, including the reference instruments themselves** — `^NSEI` does get a beta-vs-Nifty column (mathematically exactly 1.0), `GOLDBEES.NS` does get a gold-return column (exactly equal to its own return). This was originally special-cased to skip these as "degenerate," which seemed reasonable until Phase 4 pooling exposed why it was wrong — see the findings below.
- **Adjusted prices, not raw prices, everywhere**: every price-based feature uses `adj_close`/`adj_high`/`adj_low` (split & dividend back-adjusted), never raw `close`/`high`/`low`. Yahoo only provides an adjusted Close, so `adj_high`/`adj_low` are derived in the cleaning layer by scaling raw High/Low by the same factor (`adj_close / close`) Yahoo applied to Close — otherwise a High/Low-based indicator like ATR would see a fake volatility spike at every split date even though Close itself was handled correctly.
- **Pooled cross-sectional model, not one model per instrument**: all 23 instruments are trained together as one panel (`backend/app/models/dataset.py`), with `sector` (not raw `ticker`) as a categorical feature. A single instrument's ~5,000 rows is too little/noisy to train on alone; pooling gives ~110k rows and lets the model learn relationships that generalize across stocks. `sector` lets it still specialize somewhat without effectively memorizing per-stock identity the way one-hot-encoding all 23 tickers would.
- **Purged, embargoed, expanding-window walk-forward CV** (`backend/app/models/cv.py`) is the one piece of infrastructure every later modeling phase depends on, so it was built and tested before any model was fit. Two leakage mechanisms handled: *purge* drops any training row whose `label_end_date` extends into the test period (exact, using the value stored in Phase 3 — not a guess); *embargo* additionally drops a buffer of days immediately before the test period, as a safety margin against serially correlated features that purging alone doesn't cover. Folds are calendar-year test blocks; verified on real data (`initial_train_end='2013-12-31'`, `embargo_days=5`) to produce 13 folds (2014-2026) with an expanding train set (28k -> 105k rows) and, notably, a strikingly stable ~30-37% label positive rate in every single fold — a good sign the split isn't leaking or behaving erratically across very different market regimes (2016 demonetization, 2020 COVID crash, 2022 rate hikes all fall inside these folds).
- **Gradient boosting library: LightGBM** over sklearn's `HistGradientBoostingClassifier` (used only as Phase 4d's untuned gut-check) or XGBoost — chosen for CV/interview name recognition, speed, and native categorical support, at the cost of one new dependency (installed cleanly on this machine's correctly-configured Windows Python — see [[env-msys-python-shadowing]]).
- **Hyperparameter tuning: once on an isolated validation split, not per-fold or via nested CV.** Tuning separately for all 13 outer folds would be expensive and isn't standard practice; nested CV would be more rigorous but was judged excessive for this project's scope. Instead, a panel restricted to dates before the earliest outer test year is split once (reusing the same purged-splitter infrastructure) into a dev-train/dev-validation pair, a small explicit grid is searched by **log-loss** (matching the project's actual evaluation goal, not accuracy or AUC), and the winning hyperparameters are applied as fixed values across all 13 real outer folds. Documented limitation: this risks mildly overfitting the hyperparameter choice to the one validation period's quirks.
- **Calibration source: each fold calibrated using prior folds' genuine out-of-sample predictions, not a nested train-time split.** Rather than carve yet another inner purge/embargo split within each outer fold's training window, each fold's calibrator (Platt/isotonic) is fit on real held-out predictions from before that fold's test period — predictions the model already produced during walk-forward evaluation, on data it never trained on. Two variants tried: `window="last"` (only the immediately preceding fold, ~6k rows) and `window="expanding"` (all prior folds pooled, thematically consistent with the expanding-window training used everywhere else). Expanding modestly outperformed last-only (more stable for isotonic regression in particular, which needs more data to avoid overfitting a noisy step function) and was adopted as the default — see findings below for why neither ultimately mattered much here.
- **Explainability targets one final model trained on all history, not the 13 walk-forward models.** Walk-forward evaluation exists to validate methodology (does this approach generalize across time) — there's no single model there to point SHAP at, and averaging across 13 differently-trained models would muddy the "why did this specific prediction happen" story that's the actual point of explainability. Instead, one production-style model is fit on the entire available panel using the Phase 5 tuned hyperparameters (still tuned on the same pre-2014 dev split, never touching data this final model trains on), and that's what gets explained. `shap.TreeExplainer` is used without real debate — for a tree ensemble it computes exact Shapley values from the tree structure directly, not a slow model-agnostic approximation.

## Data quality findings from Phase 1 (real, not hypothetical)

- **`TATAMOTORS.NS` returned HTTP 404.** Root cause: Tata Motors demerged on 2025-10-01 into `TMPV.NS` (passenger vehicles + JLR) and `TMLCV.NS` (commercial vehicles); the old ticker stopped resolving. Swapped the universe to `TMPV.NS`. Its pre-demerger history reflects the old combined entity, not passenger-vehicles-only — a structural break to keep in mind if this stock's features look inconsistent pre/post 2025-10-01.
- **`GOLDBEES.NS` has `Open = 0.0` for its first ~247 trading days (2009-2010)**, likely thin trading shortly after listing. Resolved in Phase 2 cleaning by *not* treating `Open` as a core column: no feature we compute uses raw Open, so these rows are left as-is rather than truncated (truncating would have destroyed real, valid Close/Volume data for no benefit). GOLDBEES also has ~353 mid-series rows with a bad price or zero volume scattered through its history (mostly early, thin-trading years) — flagged as a warning, not dropped, per the mid-series-vs-leading distinction below.
- **`NESTLEIND.NS` has a completely flat price and zero trading volume for its first ~5 years (2005-01-03 to 2010-01-07, 1238 rows).** This is vendor placeholder data, not a real market condition — no real instrument trades at an unchanged price with zero volume for five years. Generalized the cleaning truncation rule from "leading non-positive price" to "leading non-positive core price OR zero volume" to catch this class of issue; NESTLEIND's usable history now correctly starts 2010-01-08, and its feature warm-up rate went from 77% to 95% (in line with peers).
- **The NESTLEIND fix above initially broke `^NSEI` and `^NSEBANK`.** Both indices legitimately have `Volume == 0` for years at a time (`^NSEI`: its entire 2007-2013 history) — Yahoo doesn't populate real trade volume for an index, only for the securities that make it up, while the index *price level* moves completely normally over that period (verified: non-zero std, realistic 2007-2013 values including the financial crisis). The generalized zero-volume-means-fake rule, written with stocks/ETFs in mind, wrongly truncated 5+ years of valid Nifty history. Caught by an unexpectedly low cross-asset feature warm-up rate on Phase 2c features that depend on the Nifty series, not by inspection. Fixed by scoping the zero-volume check to `AssetClass.STOCK`/`COMMODITY` only — indices are checked on price validity alone.
- **Cross-asset feature coverage**: any feature derived from `SILVERBEES.NS` (`silver_return_*`, `gold_silver_ratio`) is only defined from its 2022 listing onward — about 4 years out of the ~20-year stock histories. A naive "drop any row with a NaN feature" policy at the modeling stage would therefore throw away ~80% of the dataset; Phase 4/5 must decide per-experiment whether to include silver-derived features (accepting a recent-period-only model) or exclude them (keeping full history). Excluding silver-derived columns, most stocks are warmed up on 80%+ of their history; the two indices sit lower (64-72%) purely from stacking warm-up costs (own SMA-200 window + gold's 2009 start + the 60-day beta/correlation window), not a further bug.
- **`build.py` was using raw `close` instead of `adj_close` since it was first written in Phase 2b** — found while designing Phase 3 labels, by checking what price series build.py actually referenced against the Phase 1 decision to use `adj_close`. Real magnitude on `INFY.NS`: `adj_close` was as low as 63% of raw `close` early in its history (accumulated splits/dividends), with 5291/5356 rows differing at all. This would have injected a fake return spike at every split/dividend date into every single price-based feature, and would have directly corrupted Phase 3's labels. Fixed by switching all price-based computation to `adj_close`/`adj_high`/`adj_low` (see above) and adding a regression test (`test_uses_adjusted_prices_not_raw_close`) that fails if this regresses again. Verified on real `INFY.NS` data post-fix: no unadjusted-split-style artifacts remain (the only >15% single-day moves left are real events, e.g. the 2013-04-12 post-earnings crash).
- **Skipping cross-asset features for reference instruments themselves (Phase 2c's original design) broke model fitting in Phase 4c.** `^NSEI`'s own feature file had no `beta_*_vs_nifty`/`corr_*_vs_nifty`/`excess_return_*_vs_nifty` columns, and `GOLDBEES.NS`'s had no `gold_return_*` columns — those instruments' feature files had a different column set than everyone else's. Invisible until Phase 4 pooled all instruments with `pd.concat`, which silently filled the missing columns with NaN for every row of the instrument lacking them (rather than raising), which then broke `LogisticRegression.fit` with a NaN-input error far from the actual cause. Fixed by computing cross-asset features uniformly for every instrument (`beta(x,x)=1`, `corr(x,x)=1`, `excess_return(x,x)=0` are mathematically exact self-comparison values, not fabricated ones — simpler and more correct than the special-casing it replaced). Added two guards against this bug class recurring: a test asserting every instrument's feature file has identical columns, and a loud `ValueError` in `load_modeling_dataset` if it ever detects inconsistent columns across instruments before concatenating.
- **Phase 4c baseline result at k=0.5: near-random.** Logistic regression on the full feature set, evaluated across 13 walk-forward folds (2014-2026), achieved ROC-AUC of only 0.546 (5-day horizon) / 0.531 (20-day horizon) — barely above the 0.5 no-skill line — and was statistically tied with (5-day) or worse than (20-day, and log-loss in both) the naive baseline of "always predict the training set's historical average positive rate." Legitimate, not a bug: liquid large-cap NSE stocks are reasonably efficiently priced, and a linear model over technical/statistical indicators alone has limited room to find signal in small (0.5-sigma) moves. A suspiciously strong result here would have been more concerning (likely leakage) than this weak one.
- **Phase 4d diagnostic detour — is the problem the model, or the target?** Rather than assume Phase 5's gradient boosting would fix Phase 4c's weak result, tested the hypothesis directly using infrastructure already built:
  1. **Univariate correlation and mutual information** (`app/models/diagnostics.py`): every feature's linear correlation with the label was tiny (strongest was `bb_width` at -0.036). Mutual information showed `gold_return_5d`/`gold_return_20d` at ~0.095 — roughly 5x every other feature, which looked like a promising lead until checked: gold's return is a pure macro (date-level) variable, duplicated identically across all 23 instruments on any given date (4309 unique values across 4313 unique dates). Its correlation with the date-level *average* label rate was only -0.017 — essentially zero. The elevated MI is most likely a known artifact of k-NN-based mutual information estimators, which are sensitive to exact duplicate values (a macro feature repeated ~25x per date across the pooled panel is exactly that pathological case) — flagged explicitly rather than either trusted or ignored, since neither univariate statistic is as trustworthy as an actual out-of-sample test.
  2. **The decisive test: same walk-forward protocol, nonlinear model.** Ran `HistGradientBoostingClassifier` (untuned — a gut-check, not Phase 5 proper) through the identical purged/embargoed folds used for the logistic regression baseline. Result: no improvement (mean ROC-AUC 0.542 vs logreg's 0.546; Brier slightly worse). A nonlinear model did **not** recover signal the linear model missed — strong evidence the issue was the *target*, not model flexibility.
  3. **Testing larger thresholds**: re-ran the same comparison with labels computed on the fly (`load_modeling_dataset_with_k`, reusing k=0.5's persisted-label infra without overwriting it) at k=1.0 and k=1.5. ROC-AUC climbed to ~0.58 (k=1.0) and ~0.61-0.62 (k=1.5), consistently on both horizons. This is the real finding: **predictability lives in larger, less noise-dominated moves**, not small ones.
- **`k` adopted as 1.5 project-wide; official labels and baseline regenerated.** Full walk-forward re-run against the real k=1.5 target confirms the diagnostic: mean ROC-AUC 0.610 (5d) / 0.618 (20d) across all 13 folds, every single fold above 0.5 (range ~0.575-0.68). One genuinely new and important finding this surfaced: **even with real ranking signal (good AUC), Brier score and log-loss are still roughly tied with or slightly worse than the naive baseline** — the model can rank which rows are more likely positive, but its raw probabilities are poorly calibrated. That combination (real discrimination, poor calibration) is precisely the problem Phase 6 exists to solve, and it's now a concretely motivated one rather than a checkbox. A related, explainable regime-sensitivity finding: the 2020 fold's log-loss spiked badly (0.514 vs 0.297 naive, 5-day horizon) — the linear model was confidently wrong during the COVID crash, consistent with a static linear model extrapolating pre-crisis relationships poorly into unprecedented volatility. Full results: `data/results/baseline_logreg_{5,20}d.csv` and `data/results/diagnostic_*.csv`.
- **Phase 5 result: tuned LightGBM shows real, consistent improvement — the first model to beat the naive baseline on probability quality, not just ranking.** Hyperparameters (`num_leaves`, `learning_rate`, `min_child_samples`, `n_estimators`, `reg_lambda`) were tuned once on an isolated validation split entirely before the outer folds' test period (2012, carved from a panel restricted to dates before 2014-01-01 via the same purged-splitter infrastructure — never tuning on data an outer fold would later test on), selecting by log-loss, then applied as fixed values across the same 13 outer walk-forward folds used for every other model.

  | Model | 5d AUC | 5d Brier | 5d Log-loss | 20d AUC | 20d Brier | 20d Log-loss |
  |---|---|---|---|---|---|---|
  | Naive baseline | 0.500 | 0.0804 | 0.2984 | 0.500 | 0.0924 | 0.3321 |
  | Logistic regression | 0.610 | 0.0811 | 0.3124 | 0.618 | 0.0948 | 0.3503 |
  | Untuned GBM (Phase 4d gut-check) | 0.616 | 0.0816 | 0.2984 | — | — | — |
  | **Tuned LightGBM** | **0.624** | **0.0796** | **0.2918** | **0.640** | 0.0925 | **0.3269** |

  The meaningful jump isn't just AUC (0.610 -> 0.624 for 5d) — it's that tuned LightGBM's 5-day Brier (0.0796) and log-loss (0.2918) are the first results in the whole project to actually beat the naive baseline, not just tie or lose to it. Both logistic regression and the untuned gut-check GBM had real ranking signal (AUC meaningfully above 0.5) but couldn't translate it into probabilities better-calibrated than "just predict the historical base rate" — tuning closed part of that gap. The 20-day Brier (0.0925 vs naive 0.0924) is still essentially tied despite a strong 0.640 AUC — that residual discrimination-without-calibration gap is exactly Phase 6's target. One documented simplification: hyperparameters were tuned on a single validation split rather than nested cross-validation, which risks mildly overfitting the choice to that period's quirks — reasonable for this project's scope, but worth stating rather than hiding. Full results: `data/results/gbm_tuned_{5,20}d.csv`.
- **Phase 6 result: post-hoc calibration does not meaningfully improve the tuned LightGBM's probabilities — a genuine negative result, reported as such rather than forced.** Fit Platt/sigmoid scaling and isotonic regression on top of the raw scores, using each fold's prior out-of-sample predictions as the calibration-fitting data (see decision above), compared via Brier, log-loss, ROC-AUC, and Expected Calibration Error, pooled across the 12 folds with a prior fold to calibrate from:

  | Horizon | Variant | Brier | Log-loss | ROC-AUC | ECE |
  |---|---|---|---|---|---|
  | 5d | Raw | 0.0784 | 0.2881 | 0.6286 | 0.0192 |
  | 5d | Sigmoid | 0.0785 | 0.2896 | 0.6286 | 0.0224 |
  | 5d | Isotonic | 0.0783 | 0.2935 | 0.6267 | 0.0189 |
  | 20d | Raw | 0.0885 | 0.3149 | 0.6427 | 0.0403 |
  | 20d | Sigmoid | 0.0884 | 0.3194 | 0.6427 | 0.0471 |
  | 20d | Isotonic | 0.0886 | 0.3265 | 0.6374 | 0.0436 |

  (ROC-AUC is included as a sanity check, not a calibration metric: both calibrators are monotonic transforms, so AUC should be unchanged or barely moved by calibration — confirmed here, and enforced by a dedicated test, `test_calibration_does_not_change_ranking_ability`.) Neither method shows a consistent, meaningful win over raw across Brier/log-loss/ECE — differences are within noise, and isotonic even has a slightly worse log-loss at both horizons. The reliability diagrams (`data/results/reliability_diagram_{5,20}d.png`) confirm this visually: raw, sigmoid, and isotonic curves are nearly indistinguishable and already close to the diagonal in the region where the data actually lives (predicted probabilities cluster in ~0.03-0.2, matching the ~9% positive rate).

  Two things worth being honest about in the process: (1) the `window="last"` calibration-source variant was tried first and looked *slightly worse* than raw on every metric — before concluding "calibration doesn't help," checked whether that specific design choice (only ~6k rows of calibration data, likely too little/noisy for isotonic in particular) was the limiting factor, rather than treating the first negative result as final. Trying `window="expanding"` (pooling all prior folds, thematically consistent with the expanding-window training used elsewhere) modestly improved the calibrated variants but didn't change the conclusion. (2) This negative result is consistent with the ML literature: Niculescu-Mizil & Caruana's well-known calibration study found boosted-tree ensembles are often already reasonably well-calibrated (unlike SVMs or raw boosting margins, which tend to need Platt scaling badly) — a tuned LightGBM model apparently doesn't have the kind of systematic, sigmoid- or monotonic-shaped bias that post-hoc calibration is designed to fix. **Decision: keep the tuned LightGBM's raw probabilities as the project's output**; the calibration infrastructure (`backend/app/models/calibration.py`) is built, tested, and available, but isn't inserted into the final pipeline since it doesn't earn its complexity here.
- **Phase 7 result: `realized_vol_20d` dominates global SHAP importance by ~4x — an interpretive finding, not just a chart.** SHAP (`shap.TreeExplainer`) on a final LightGBM trained on all available history ranks features by mean |SHAP value|:

  | Rank | 5d model | 20d model |
  |---|---|---|
  | 1 | `realized_vol_20d` (0.372) | `realized_vol_20d` (0.503) |
  | 2 | `realized_vol_60d` (0.091) | `realized_vol_60d` (0.133) |
  | 3 | `volume_ratio_20` (0.066) | `sma_200` (0.064) |

  and both the summary plot and individual example explanations (e.g. `HDFCBANK.NS`'s highest 5-day probability on 2026-09-01, driven mostly by unusually *low* `realized_vol_20d`) show a completely consistent direction: **low current volatility pushes predicted probability up.** This is worth thinking through, not just reporting: the label threshold is itself `k × current_vol × sqrt(N)`. If volatility persisted perfectly from today into the forward window, this would be self-canceling — a return scaled by its own realized volatility compared against a threshold scaled by that same volatility gives a probability independent of the vol level. But volatility is well-documented to *mean-revert* (a calm period tends toward more volatility, not less), so when current volatility is unusually low, the threshold is set low relative to what volatility will likely actually be over the forward window — mechanically making the bar easier to clear, largely independent of genuine directional edge.

  To be precise about what this is not: it is not leakage (`realized_vol_20d` is a purely trailing, already-known quantity at prediction time) and it is not necessarily undesirable to predict (volatility-regime dynamics are real and useful information). But it does mean a meaningful part of the model's demonstrated edge (Phases 5-6's AUC of 0.62-0.64) likely reflects **learned volatility mean-reversion interacting with the label's own construction**, not pure directional/momentum signal — an important nuance for how Phase 8's backtest and any eventual dashboard should describe what the probability actually represents to a user.

  A validating cross-check: `gold_return_20d`, which Phase 4d's mutual-information diagnostic suspiciously ranked ~5x more important than every other feature (flagged then as a likely k-NN estimator artifact from a duplicated macro feature), shows up in SHAP's real importance ranking for the 20-day model at ~14th place (0.025) — roughly 20x smaller than `realized_vol_20d`, not dominant. SHAP, computed from the actual fitted model's real predictions rather than a standalone univariate statistic, directly corroborates the earlier skepticism. Full results: `data/results/shap_global_importance_{5,20}d.csv`, `shap_summary_{5,20}d.png`, `shap_example_explanations_{5,20}d.csv`.
